# 详细设计规范

> 本规范定义详细设计文档（Detailed Design Document，DDD）的编写要求。
>
> 所有新功能、重大改动、架构调整均应先完成详细设计，经确认后方可进入编码阶段。

---

# 目的

详细设计文档用于：

- 明确业务需求
- 分析现有实现
- 设计技术方案
- 评估影响范围
- 控制实施风险
- 拆分开发任务

设计文档应作为开发、测试、Review 的共同依据。

---

# 适用场景

以下情况必须编写详细设计：

- 新增业务功能
- 新增模块
- API 调整
- 数据库结构调整
- 状态管理调整
- 架构调整
- 大型重构

以下情况可以跳过（**唯一口径见 `references/hard-gate.md`「三级判定（唯一权威）」表**，本处与之一致）：

- Bug 修复
- 文案修改
- 样式调整
- 配置修改
- 纯文档修改

> 可跳过仅为分类判定，须经用户确认后方可跳过，未确认不得默认跳过。

---

# 设计原则

所有设计必须遵循以下原则：

## KISS（保持简单）

优先采用简单、易理解的方案，避免不必要的复杂设计。

---

## DRY（避免重复）

优先复用已有能力，避免重复实现。

---

## 单一职责（SRP）

模块职责单一，一个模块只负责一件事情。

---

## 低耦合高内聚

模块之间保持低耦合，模块内部保持高内聚。

---

## 组合优于继承

优先组合，而不是继承。

---

## 向后兼容

保持向后兼容。

未经确认不得修改：

- Public API
- 公共组件
- 数据格式
- 数据库结构

---

## 最小改动

遵循最小改动原则。

只修改实现需求所必须修改的部分。

避免扩大影响范围。

---

## 复用优先

设计之前必须先分析：

- 是否已有模块
- 是否已有组件
- 是否已有 API
- 是否已有工具类

优先复用已有实现。

---

## 概设落实（Overview-Driven）

详细设计**根据阶段一产物（概设 + UI 原型）实现**：概设契约（后端概设领域模型 / 状态机 / 数据字典 / 接口契约 / 权限 / 消息事件 + 前端概设页面与路由 / API 模块）+ `<项目根>/prototype/` 下的原型（Vue SFC，真 `te-*` 组件组合：区域→组件 / 交互 / 状态覆盖；交接件 `archive-spec/product/ui-*/_notes.md`）在设计文档中逐项落实为具体方案。

- 设计文档的每一项都应在概设中有依据，不偏离、不新增概设外内容
- 超出概设范围的方案，先回到阶段一确认，再进入设计

---

# 必要章节

每份设计文档必须包含以下章节。

---

## 1. 背景（Background）

说明为什么需要开发此功能。

包括：

- 业务背景
- 问题描述
- 当前痛点

不要描述实现方案。

---

## 2. 目标（Goal）

说明本次开发最终要达到什么目标。

包括：

- 功能目标
- 非功能目标
- 成功标准

---

## 3. 阶段一产物（Phase-1 Products）

**引用阶段一归档产物**（后端概设 `overview-be-*.md` + 前端概设 `overview-fe-*.md`，在 `archive-spec/product/` 下；原型 `.vue` 在 `<项目根>/prototype/` 下，交接件 `archive-spec/product/ui-*/_notes.md`），不完整重述。阶段一产物为唯一需求来源，**详细设计据此逐项实现**：概设契约 + UI 原型（区域→组件/交互/状态覆盖）在设计章节（§5）逐项落实，每项设计有阶段一产物依据；超出阶段一范围的需回到阶段一确认，禁止自行补全。

此处仅补充：

- 需求摘要
- 阶段一产物未覆盖的技术性边界
- 需求歧义的最终裁决记录

如果需求存在歧义，应记录待确认事项。

---

## 4. 当前状态（Current State）

分析当前系统。

至少回答：

- 是否已有类似功能？
- 哪些模块可以复用？
- 哪些代码需要修改？
- 是否已有公共组件？
- 是否已有 API？

不要重复设计。

重点说明"现在是什么"。

---

## 5. 设计方案（Solution Design）

说明准备如何实现。

必须包含：

### 5.1 模块设计

描述：

- 新增模块
- 修改模块
- 模块职责
- 依赖关系

---

### 5.2 数据模型

如果涉及：

- Entity
- DTO
- Store
- Cache
- 数据库

说明新增、修改、删除。

---

### 5.3 API 设计

如果涉及接口，描述：

- Request
- Response
- Error
- 兼容性

不要只写 URL。

---

### 5.4 UI / 页面交互

如果涉及页面，说明：

- 页面变化
- 组件变化
- 交互流程
- Loading
- Empty
- Error

---

### 5.5 异常处理

说明异常处理策略。

包括：

- 参数异常
- 网络异常
- 权限异常
- 业务异常

---

## 6. 设计决策（Design Decisions）

所有重要设计都必须说明设计依据。

每个设计决策至少包含：

### 决策内容

描述最终采用的方案。

### 可选方案

至少列出一种备选方案。

### 最终方案

说明最终选择。

### 选择原因

包括：

- 为什么选择当前方案
- 为什么放弃其他方案

### 优点

分析优势。

### 缺点

分析不足。

### 长期影响

分析：

- 扩展性
- 可维护性
- 技术债务

## 7. 方案对比（Alternative Analysis）

对于关键设计，应至少提供两种可行方案。

每种方案应分析：

- 实现复杂度
- 开发成本
- 可维护性
- 可扩展性
- 性能
- 风险

最终说明为什么选择当前方案。

## 8. 设计假设（Assumptions）

列出设计成立所依赖的重要前提。

例如：

- 当前数据库结构保持不变
- 权限模型保持不变
- API 返回格式保持一致
- 第三方接口保持兼容

如果上述假设发生变化，应重新评估设计方案。

## 9. 影响范围（Impact Analysis）

必须分析：

- Module
- API
- Database
- Store
- UI
- Config
- CI/CD
- Documentation

分别说明新增、修改、删除，以及影响原因。

## 10. 风险与兼容性（Risks & Compatibility）

至少分析：

- Breaking Change
- Backward Compatibility
- Performance
- Security
- Scalability
- Data Migration
- Upgrade
- Rollback
- Technical Debt

每项风险必须提供：

- 风险描述
- 影响范围
- 解决方案

## 11. 实施策略（Implementation Strategy）

说明开发顺序。

推荐按照依赖关系划分：

```
Phase 1  基础能力
    ↓
Phase 2  数据层
    ↓
Phase 3  业务层
    ↓
Phase 4  接口层
    ↓
Phase 5  页面层
    ↓
Phase 6  测试
```

说明为什么采用当前顺序。

## 12. 实施计划（Implementation Plan）

每个任务必须包含：

- Task 名称
- 开发目标
- 涉及模块
- 修改文件
- 前置依赖
- 验收标准

要求：

- 可独立开发
- 可独立测试
- 可独立 Review
- 可独立回滚


## 13. 验收标准（Acceptance Criteria）

为每个主要功能制定验收标准。

例如：

- 功能符合需求
- API 返回正确
- 页面展示正确
- 权限校验正确
- 回归测试通过

所有标准必须可验证。

---

## 14. 测试方案（Test Plan）

至少包含：

- 正常流程
- 异常流程
- 边界测试
- 兼容性测试
- 回归测试

说明如何验证设计正确。

**执行说明**：测试方案由**人工执行**；自动化覆盖由 `npm run ts-check && npm run lint:html && npm run lint:css && npm run build` 承担，在 implement 阶段完成后运行。

---

## 15. 待确认事项（Open Questions）

记录仍需确认的问题。

例如：

- 产品确认
- UI 确认
- API 确认
- 数据迁移方案

如果为空，应写"无"。

---

# AI 指令

AI 在生成详细设计时必须：

1. 先分析现有项目，再提出设计。
2. 优先复用已有模块，而不是新增模块。
3. 设计方案逐项落实概设契约（每项设计有概设依据，无概设外新增）。
4. 不得直接进入编码阶段。
5. 不得跳过风险分析。
6. 每个设计决策应说明原因。
7. 如需求不明确，应停止并提出问题。
8. 最终输出必须符合 `references/templates/design.md` 的结构。

未经用户确认，不得进入 Implementation 阶段。

# 设计门禁

详细设计只有满足以下条件后，才允许进入开发阶段：

- [ ] 需求明确
- [ ] 已逐项落实概设契约（每项设计有概设依据，无概设外新增）
- [ ] 当前实现分析完成
- [ ] 技术方案完成
- [ ] 已完成设计决策
- [ ] 已完成方案对比
- [ ] 已完成设计假设
- [ ] 已分析影响范围
- [ ] 已分析风险
- [ ] 已制定实施策略
- [ ] 已拆分开发任务
- [ ] 已定义验收标准
- [ ] 已生成详细设计文档
- [ ] 用户已确认设计

未满足上述任一条件：

- 禁止进入编码阶段。
- 禁止生成生产代码。
- 禁止修改项目源码。
